# Persistent Entity Identity

Names for things that have to survive a restart.

Related: [WorldPersistence.md](WorldPersistence.md),
[ADR-006](../ADR/ADR-006-delta-persistence.md).

---

## Why this is the hard part

A delta is worthless without a name for what it applies to, and "the third tree
in that patch" is not a name - it is a position in an array that the next change
to the placement rules will renumber. Get identity wrong and a removal recorded
today deletes a different tree tomorrow.

Identity must not depend on: Actor names, pointers, spawn order, array index, a
GUID regenerated each run, memory addresses, or the iteration order of any map.
The same list as ProceduralGeneration.md's, for the same reason - anything with
process lifetime produces a name that means something different tomorrow.

---

## Two kinds of thing

**Procedural entities** already exist in the base world. Their identity is
*derived*, not assigned:

```
id = hash(planet key, patch id, layer, cell x, cell y,
          terrain version, environment version)
```

The same tree computes the same id on every machine and in every run, because it
is a hash of where the generator put it. Nothing has to be written down for a
tree to have a name - which is exactly what makes "tree 817291 is removed" a
complete statement about a world containing billions of them.

**Created entities** do not exist in the base world, so their identity has to be
*assigned*: a random 128 bits. Locally that is a UUID; when a server arrives it
becomes the server's to allocate and nothing else changes.

The kind is stored in the top eight bits of the id, so a bare id is
self-describing and applying a removal to a created entity is impossible rather
than merely unlikely.

### Why 128 bits

The procedural case would fit in 64. The created case would not: a random 64-bit
id reaches a 50% collision chance at four billion entities, which sounds like a
lot until it is a shared universe with years of history. Sharing one type for
both is worth more than eight bytes a row.

## The placement cell is the name

A vegetation instance carries the patch and grid cell it was placed from, and
that is the only stable name it has. Its index in the output array is not:
adding a slope filter or retuning a density renumbers every instance after the
first change.

The cell does not move when the rules change. It either produces something or it
does not.

### The bug this caused, and the rule it produced

The vegetation scatter originally capped its grid resolution by the caller's
instance budget, to respect a per-patch limit. That made the *grid* a function of
a runtime tuning value - so a tree chopped by a command using a budget of 4000
had a different name than the same tree generated by the streamer at 2000, and
came back after a restart.

> **A runtime budget must never participate in identity.**

The grid is now a function of the patch and the biome table alone, and the budget
is applied as a per-cell keep roll with its own hash stream. Cells stay where
they are; a budget-limited patch is uniformly sparser rather than renumbered.

**Presence still depends on the budget; identity does not.** A tree that two
callers disagree about is absent for one of them, but it is the same tree.

---

## Generation versions are part of the name

Both the terrain and environment generation versions are folded into a
procedural entity's id.

That is deliberate and it is not defensive. A bump to either genuinely changes
which vegetation exists, so a removal recorded under the old version must **stop
matching** rather than silently deleting whatever now occupies that address. The
removal becomes inert, which is the correct outcome for a statement about a world
that no longer exists.

---

## Region identity

`FPersistenceRegionId` is a cube-sphere address plus the planet key. Its level is
chosen once per planet from the radius, targeting a constant 2 km region, and is
stored in the id - a region read from the database must not change meaning if the
targeting rule is retuned.

Its 64-bit key **packs** face, level and coordinates rather than hashing them:

```
face   3 bits    level  5 bits    X  28 bits    Y  28 bits
```

Packing is exact and can be taken apart again by anyone reading the database. A
hash would be shorter to write and one birthday collision away from silently
merging two settlements.

The planet key stays a separate column rather than being mixed in, so a query can
ask for one planet's regions without unpacking anything, and two planets cannot
collide because the pair is the key.

## Testing

Three test bodies, all standalone:

`Universe.Planet.PersistenceRegionIdentity` - regions are deterministic, the
level targeting hits its size at four planet radii, the packed key round-trips
its address exactly, nearby points share a region and spread points do not, and
**two planets with the same radius produce the same address but different
regions** - the case that would be dangerous if the planet were not part of the
identity.

`Universe.Planet.PersistentEntityIdentity` - 576 derived ids are unique and
reproducible; every input is part of the name, including cell order (5,7 is not
7,5) and both generation versions; created ids are unique across 4096 draws;
text and binary round-trips; and malformed text is **rejected rather than parsed
as zero**, because a zero id would read as "kind None" and be quietly skipped,
which looks like data loss rather than the corruption it is.

`Universe.Planet.VegetationPersistentIdentity` - runs the real scatter over six
patches on five cube faces, names every instance, and checks the names are
unique within a patch-layer and reproduced exactly when the patch is scattered
again. This is the test that makes "remove tree 817291" meaningful.
